# Техническая документация проекта dryad_vault

Документ описывает архитектуру, структуру компонентов, схему базы данных, сценарии обработки данных, серверную конфигурацию и процессы обслуживания Telegram-бота `dryad_vault`.

---

## 1. Архитектура и концепция

Бот решает задачу контролируемой выдачи персонального медиаконтента (видео и фото) клиентам с минимальными накладными расходами на дисковую подсистему сервера и соблюдением требований к приватности данных.

### Ключевые архитектурные принципы
1. **Zero-Disk Storage для медиа:**
   * Сервер не сохраняет медиафайлы на локальном диске (NVMe).
   * Файлы физически хранятся на серверах Telegram.
   * Бот оперирует исключительно строковыми идентификаторами `file_id`.
2. **Изолированный архив (`ARCHIVE_CHANNEL_ID`):**
   * Закрытый частный Telegram-канал используется как постоянное хранилище медиа и точка создания резервных копий базы данных.
   * Предварительная пересылка в канал гарантирует, что `file_id` останется валидным для бота бессрочно, даже если клиент удалит чат или сообщение.
3. **Минимизация собираемых данных (152-ФЗ):**
   * В таблицах хранятся только системный Telegram `user_id` и публичный `@username`.
   * Имена, фамилии, телефонные номера и платежные реквизиты не запрашиваются и не сохраняются.
4. **Защита от утечки материалов:**
   * Отправка медиафайлов клиентам выполняется с параметром `protect_content=True`, блокирующим пересылку, сохранение на устройство и создание скриншотов/записи экрана в официальных клиентах Telegram.

## 3. Схема базы данных (SQLite / aiosqlite)

Данные сохраняются в локальном файле `asmr_orders.db`. Инициализация и авто-миграции выполняются функцией `database.init_db()`.

### Таблица `orders`
Хранит записи о выданных и ожидающих активации материалах.

| Колонка | Тип | Ограничения | Назначение |
|---|---|---|---|
| `code` | `TEXT` | `PRIMARY KEY` | Уникальный URL-safe идентификатор заказа (`secrets.token_urlsafe(8)`). |
| `file_id` | `TEXT` | `NOT NULL` | Идентификатор медиафайла в архивном канале Telegram. |
| `is_used` | `INTEGER` | `DEFAULT 0` | Статус: `0` — ожидает активации, `1` — активирован или выдан напрямую. |
| `used_by` | `INTEGER` | `NULLABLE` | Telegram `user_id` владельца заказа. |
| `title` | `TEXT` | `NULLABLE` | Название ролика или фото. |
| `media_type` | `TEXT` | `DEFAULT 'video'` | Тип объекта: `'video'` либо `'photo'`. |

### Таблица `users`
Справочник пользователей, взаимодействовавших с ботом.

| Колонка | Тип | Ограничения | Назначение |
|---|---|---|---|
| `user_id` | `INTEGER` | `PRIMARY KEY` | Системный числовой Telegram ID пользователя. |
| `username` | `TEXT` | `NULLABLE` | Никнейм без префикса `@`. |

## 4. Потоки данных и сценарии работы

### Сценарий 1: Генерация одноразовой ссылки администратором
1. Администратор отправляет фото или видеофайл боту.
2. `services.extract_media_info()` извлекает метаданные:
   * Тип медиа (`video` или `photo`).
   * Имя файла или текст подписи. Если названия нет, включается состояние FSM `AdminUpload.waiting_for_title`.
3. Бот передает файл в канал `ARCHIVE_CHANNEL_ID` через `services.backup_and_get_file_id()` и фиксирует постоянный `file_id`.
4. В таблицу `orders` записывается новая строка с уникальным `code`, `is_used=0`, `used_by=NULL`.
5. Срабатывает отправка копии базы данных в архивный канал (`services.backup_database()`).
6. Бот возвращает администратору карточку с кодом и deep-link ссылкой вида `https://t.me/<bot_username>?start=<code>`.

### Сценарий 2: Активация материала клиентом
1. Пользователь запускает бота по ссылке `t.me/<bot_username>?start=<code>` или отправляет команду вручную через «🎬 Забрать заказ».
2. `services.register_or_update_user()` фиксирует `user_id` и `@username` в таблице `users`. При обнаружении нового пользователя или смене юзернейма создается резервная копия БД.
3. Вызывается `database.redeem_code(code, user_id)`:
   * **Дубликат:** если файл с таким `file_id` уже числится за клиентом, временный заказ удаляется из `orders` во избежание захламления интерфейса. Возвращается статус `DUPLICATE_REMOVED`.
   * **Новая активация:** запись переходит в статус `is_used=1`, `used_by=user_id`. Возвращается статус `SUCCESS`.
4. Бот вызывает `services.send_protected_media()`, передавая файл с `protect_content=True` и актуальной разметкой клавиатуры.
5. При статусе `SUCCESS` администратор получает системное уведомление об активации.

### Сценарий 3: Ручная привязка по Telegram ID
1. Администратор выбирает «📎 Привязать к ID» и указывает числовой ID заказчика.
2. `services.sync_user_from_telegram()` проверяет доступность профиля и регистрирует пользователя в `users`.
3. Администратор передает файл (фото или видео).
4. Медиафайл пересылается в канал-архив.
5. `database.create_direct_order()` привязывает объект напрямую к пользователю (`is_used=1`, `used_by=target_id`). Если материал уже был привязан ранее, дубликат не создается.
6. Выполняется резервное копирование БД в канал-архив. Заказ становится доступен клиенту в «📜 Мои материалы».

### Сценарий 4: Просмотр материала администратором
1. В панели управления администратор открывает «👥 Список заказчиков» ➔ выбирает заказчика ➔ выбирает конкретный материал.
2. В карточке нажимает кнопку «▶️ Посмотреть в чате».
3. Обработчик `handle_admin_view_media` отправляет медиафайл прямо в чат администратора без перехода на другие экраны.

## 5. Система резервного копирования (Event-Driven Backups)

Резервное копирование базы данных инициируется при изменении состояния данных на сервере.

* **Исполнитель:** `services.backup_database(bot, description)`
* **Точки вызова:**
  * Загрузка нового материала и создание ссылки.
  * Прямая привязка медиа к ID пользователя.
  * Успешная активация кода заказчиком.
  * Удаление дублирующего кода при повторном переходе.
  * Переименование объекта в базе.
  * Удаление материала из профиля клиента.
  * Регистрация нового заказчика или изменение его `@username`.
* **Финальный формат документа:** `asmr_orders_YYYYMMDD_HHMMSS.db`.
* **Описание:** Каждое сообщение с файлом содержит текстовое пояснение операции и метку времени.

## 6. Интерфейс и навигация

### Нижняя панель (Reply Keyboard)
* Клавиатуры создаются с параметром `is_persistent=True`, предотвращающим их случайное сворачивание.
* Клавиатура повторно передается при отправке каждого медиафайла, что восстанавливает кнопки на клиенте, даже если пользователь удалил предыдущие сообщения.

### Системное меню (Bot Commands)
В интерфейсе мессенджера (кнопка «Меню» в строке ввода) зарегистрирована команда:
* Для клиентов: `/start` — «Главное меню».
* Для администратора: `/start` — «Панель управления».

Это позволяет восстановить контекст бота, если чат был полностью очищен.

### Инлайн-навигация и списки
* Списки заказчиков и материалов используют постраничную пагинацию с шагом, заданным переменной `PAGE_SIZE` (по умолчанию 5 объектов на страницу).
* В карточках материалов отображаются визуальные маркеры: `🎬` для видео и `🖼` для изображений.

## 7. Переменные окружения (.env)

Файл `.env` располагается в корневой директории проекта на VPS:

```env
BOT_TOKEN=1234567890:ABCdefGHIjklMNOpqrSTUvwxyz
ADMIN_ID=123456789
DB_NAME=asmr_orders.db
ARCHIVE_CHANNEL_ID=-1001234567890
PAGE_SIZE=5
```

### Назначение параметров
* `BOT_TOKEN` — токен авторизации Telegram Bot API.
* `ADMIN_ID` — числовой идентификатор учетной записи администратора.
* `DB_NAME` — имя рабочего файла SQLite.
* `ARCHIVE_CHANNEL_ID` — числовой ID закрытого канала-архива (начинается с `-100`). Бот должен обладать правами администратора на публикацию сообщений.
* `PAGE_SIZE` — лимит записей на один экран пагинации в списках.

## 8. Развертывание и эксплуатация на Debian VPS

### Управление процессом через systemd
Конфигурационный файл: `/etc/systemd/system/dryad_bot.service`

```ini
[Unit]
Description=Dryad ASMR Telegram Bot
After=network.target

[Service]
Type=simple
User=root
WorkingDirectory=/root/dryad_vault
ExecStart=/root/dryad_vault/venv/bin/python bot.py
Restart=always
RestartSec=5
EnvironmentFile=/root/dryad_vault/.env

[Install]
WantedBy=multi-user.target
```

### Команды обслуживания
* Проверка статуса: `systemctl status dryad_bot`
* Перезапуск процесса: `systemctl restart dryad_bot`
* Остановка процесса: `systemctl stop dryad_bot`
* Просмотр логов в реальном времени: `journalctl -u dryad_bot -f`
* Просмотр последних записей: `journalctl -u dryad_bot -n 100 --no-pager`

## 9. CI/CD пайплайн (GitHub Actions)

Конфигурация автоматического деплоя находится в `.github/workflows/deploy.yml`.

### Алгоритм работы:
1. Триггер: `git push origin main`.
2. Раннер подключается к серверу по SSH, используя секреты репозитория (`HOST`, `USERNAME`, `SSH_KEY`).
3. В рабочей директории `/root/dryad_vault` выполняются команды:
   * `git pull origin main`
   * `./venv/bin/pip install -r requirements.txt`
   * `systemctl restart dryad_bot`
4. Файлы `.env` и `asmr_orders.db` не затрагиваются обновлением, так как внесены в `.gitignore`.

## 10. Аварийное восстановление (Disaster Recovery)

В случае отказа или пересоздания VPS-сервера порядок действий следующий:

1. Развернуть базовые системные пакеты на новом экземпляре:
   ```bash
   apt update && apt install -y python3 python3-venv python3-pip git
   ```
2. Склонировать проект и инициализировать окружение:
   ```bash
   git clone git@github.com:alkrvtsv/dryad_vault.git /root/dryad_vault
   cd /root/dryad_vault
   python3 -m venv venv
   ./venv/bin/pip install -r requirements.txt
   ```
3. Создать файл `.env` с боевыми параметрами доступа.
4. Открыть архивный канал в Telegram, скачать последний присланный файл `asmr_orders_*.db`, переименовать его в `asmr_orders.db` и скопировать в `/root/dryad_vault/`.
5. Создать файл `/etc/systemd/system/dryad_bot.service` и включить службу:
   ```bash
   systemctl daemon-reload
   systemctl enable --now dryad_bot
   ```
Все привязки, материалы и ссылки продолжат функционировать без рассинхронизации.
